# ADR-002: Classic Rotation Selection Methods

## Context

A classic tontine needs a deterministic recipient order for each cycle. The
order may be agreed directly by an administrator, generated by a random process,
or approved through member governance. Recipient selection must remain
reproducible and auditable after the rotation becomes active.

## Decision

The domain supports three rotation-selection methods:

1. **Administrator-defined order**: an authorized workflow supplies the ordered
   active member identifiers. This is the V1 implementation and is represented by
   `ClassicRotation.from_active_members()`.
2. **One-time randomized order**: a future workflow may generate an order once,
   then persist the random seed, algorithm/version, input member set, generated
   order, actor, and timestamp. Recipient lookup must use the persisted order and
   must never re-randomize per cycle.
3. **Vote-approved order**: a future governance workflow may submit an ordered
   rotation proposal and activate it only after the required vote threshold is
   reached. The proposal, votes, threshold, effective cycle, and final order must
   remain traceable.

All active rotation methods must produce the same immutable, validated ordered
member list consumed by `ClassicRotation`. Recipient selection remains a pure,
deterministic lookup over that list.

## Alternatives Considered

- **Randomize every time a recipient is requested**: rejected because results
  would not be reproducible and historical payout decisions could change.
- **Hide voting or randomization inside `recipient_for_cycle()`**: rejected
  because governance and selection decisions must be explicit, auditable inputs.
- **Support only administrator-defined order permanently**: rejected because
  groups may require transparent lottery-style ordering or member-approved
  rotation.

## Consequences

### Positive

- V1 stays simple and deterministic.
- Random and vote-based workflows can be added without changing recipient lookup.
- Historical rotations can be reconstructed from persisted order and provenance.
- Governance remains separate from the classic domain calculation.

### Negative or Trade-offs

- Randomization requires secure, reproducible seed and algorithm provenance.
- Vote-approved rotations require a future governance capability.
- Changing an active rotation must be an explicit versioned decision rather than
  an in-place mutation.

## Verification

- `ClassicRotation.from_active_members()` validates non-empty, unique member IDs.
- `recipient_for_cycle()` is deterministic and wraps around the persisted order.
- Future random and vote workflows must produce the same validated ordered-list
  contract and add tests for reproducibility, approval, effective cycle, and
  historical reconstruction.
